# GIS DATA PROVENANCE
## TerraMesh AI — Data Source Transparency

**Version:** Phase 2  
**Purpose:** Document the origin and reliability of all spatial data displayed in the platform

---

## OVERVIEW

Data provenance is critical for mine safety systems. Operators must know whether displayed data represents:
- Live measured data from sensors
- Simulated/demonstration data
- Static engineering reference data
- Seeded database geometry

The TerraMesh AI platform implements explicit provenance labeling throughout the spatial data pipeline.

---

## PROVENANCE TYPES

### 1. MEASURED DATA

**Description:** Real measurements from physical sensors or location systems  
**Sources:** 
- Sensor telemetry (tilt, displacement, crack width, vibration)
- Worker location (RFID, RTLS, UWB hardware)
- Environmental sensors (temperature, humidity)

**Characteristics:**
- Collected in real-time from hardware
- Stored in TimescaleDB hypertable
- Labeled with `provenance: "MEASURED"`
- Highest reliability for operational decisions

**Examples:**
```json
{
  "node_id": "NODE-017",
  "tilt": 4.8,
  "displacement": 12.4,
  "provenance": "MEASURED"
}
```

---

### 2. SIMULATION

**Description:** Simulated or demonstration data for testing and training  
**Sources:**
- Worker location simulator (`worker_location.py`)
- Demo scenario engine (`simulation.py`)
- ML model training synthetic data

**Characteristics:**
- Generated by software, not hardware
- Clearly labeled as `provenance: "SIMULATION"`
- Used for demo, training, and testing
- NOT suitable for operational decisions without validation

**Examples:**
```json
{
  "worker_id": "w-23",
  "location_source": "SIMULATOR",
  "provenance": "SIMULATION",
  "lat": 23.7758,
  "lng": 86.4142
}
```

**Hardware-Ready Schema:**
The worker location service supports future hardware sources:
- RFID → `provenance: "MEASURED DATA"`
- RTLS → `provenance: "MEASURED DATA"`
- UWB → `provenance: "MEASURED DATA"`

---

### 3. SEEDED DATABASE

**Description:** Engineering geometry seeded into the database  
**Sources:**
- `seed_spatial.py` script
- PostGIS `risk_zones` table
- PostGIS `evacuation_routes` table

**Characteristics:**
- Engineering reference geometry (survey data)
- Stored in database with PostGIS geometry columns
- Labeled as `provenance: "SEEDED DATABASE"`
- Legitimate for operational use (survey-verified)

**Examples:**
```json
{
  "id": "zone-b",
  "polygon": [[86.4100, 23.7750], [86.4160, 23.7800], ...],
  "provenance": {
    "geometry": "SEEDED DATABASE",
    "status": "SIMULATION"
  }
}
```

---

### 4. STATIC DESIGN DATA

**Description:** Design constants and fallback data  
**Sources:**
- API fallback constants in `main.py`
- Static design parameters

**Characteristics:**
- Used when database is empty (pre-seed dev)
- Labeled as `provenance: "STATIC DESIGN DATA"`
- Temporary fallback, not for production

**Examples:**
```json
{
  "id": "zone-a",
  "polygon": null,
  "provenance": {
    "geometry": "STATIC DESIGN DATA",
    "status": "SIMULATION"
  }
}
```

---

### 5. STATIC ENGINEERING REFERENCE

**Description:** Static reference geometry for visualization context  
**Sources:**
- Mine boundary (lease boundary)
- Pit bench contours
- Geological fault lines
- Underground tunnel network

**Characteristics:**
- Legitimate engineering reference data
- Stored as frontend constants (not in database)
- Should be labeled in UI as reference data
- Not operational data (context only)

**Examples:**
```javascript
// Static engineering reference (legitimate)
const MINE_BOUNDARIES = [
  [23.7820, 86.4020],
  [23.7845, 86.4190],
  ...
];
```

**Recommendation:** Add provenance label in map tooltips:
```
"Mine Lease Boundary (STATIC ENGINEERING REFERENCE)"
```

---

### 6. UNLABELED

**Description:** Data from unknown or unclassified sources  
**Sources:**
- Third-party integrations
- Manual data entry
- Unknown hardware sources

**Characteristics:**
- Labeled as `provenance: "UNLABELED"`
- Requires operator classification before operational use
- Default for `location_source: "OTHER"`

**Examples:**
```json
{
  "worker_id": "w-99",
  "location_source": "OTHER",
  "provenance": "UNLABELED"
}
```

## PROVENANCE VALIDATION

### Server-Side Derivation

**Rule:** Clients cannot self-declare provenance

**Implementation:**
```python
# worker_location.py
SOURCE_PROVENANCE = {
    "SIMULATOR": "SIMULATION",
    "RFID": "MEASURED DATA",
    "RTLS": "MEASURED DATA",
    "UWB": "MEASURED DATA",
    "OTHER": "UNLABELED",
}
```

**Result:** Provenance is derived server-side from declared source

### Audit Trail

**Rule:** All provenance changes logged

**Implementation:**
```python
audit_service.record(
    "WORKER_LOCATION_INGEST",
    detail=f"provenance={stored['provenance']}"
)
```

**Result:** Complete audit trail of provenance assignments

## PROVENANCE BEST PRACTICES

### 1. Never Hide Provenance

**Rule:** All spatial data must display its provenance

**Implementation:**
- API responses include provenance field
- UI tooltips show provenance
- Legend includes provenance section

### 2. Never Self-Declare Measured

**Rule:** Clients cannot mark their data as MEASURED

**Implementation:**
- Server derives provenance from source
- Hardware sources required for MEASURED label
- Audit trail of all provenance assignments

### 3. Clearly Label Simulations

**Rule:** Simulation data must be explicitly labeled

**Implementation:**
- SIMULATOR source → SIMULATION provenance
- Demo overlays clearly marked
- No "LIVE" claims for simulated data

### 4. Distinguish Reference from Operational

**Rule:** Static reference data must be labeled as such

**Implementation:**
- Engineering reference layers labeled STATIC ENGINEERING REFERENCE
- Operational data labeled with actual source
- UI distinguishes context from operational data

### 5. Validate Provenance Consistency

**Rule:** Provenance must match actual data source

**Implementation:**
- Database seeded geometry → SEEDED DATABASE
- Hardware measurements → MEASURED DATA
- Simulator output → SIMULATION
- Static constants → STATIC DESIGN DATA or STATIC ENGINEERING REFERENCE

## PROVENANCE TRANSITIONS

### Simulation → Measured

**Scenario:** Hardware RFID system deployed

**Transition:**
1. Worker location source changes from SIMULATOR to RFID
2. Provenance automatically changes from SIMULATION to MEASURED DATA
3. UI reflects new provenance
4. Audit trail records transition

**Implementation:**
```python
# Before
{
  "location_source": "SIMULATOR",
  "provenance": "SIMULATION"
}

# After
{
  "location_source": "RFID",
  "provenance": "MEASURED DATA"
}
```

### Static → Seeded

**Scenario:** Mine boundary added to database

**Transition:**
1. Create `mine_boundaries` table with PostGIS geometry
2. Seed engineering survey data
3. API serves from database instead of static constant
4. Provenance changes from STATIC ENGINEERING REFERENCE to SEEDED DATABASE

**Implementation:**
```python
# Before (static constant)
MINE_BOUNDARIES = [[23.7820, 86.4020], ...]

# After (database)
{
  "id": "boundary-jharia",
  "geom": <PostGIS geometry>,
  "provenance": "SEEDED DATABASE"
}
```

## PROVENANCE SECURITY

### Access Control

**Rule:** Provenance labels cannot be modified by clients

**Implementation:**
- Provenance derived server-side
- No client-provided provenance in API inputs
- RBAC controls on provenance-critical endpoints

### Audit Logging

**Rule:** All provenance assignments logged

**Implementation:**
- `audit_logs` table records provenance changes
- Include user, timestamp, previous value, new value
- Immutable audit trail

### Integrity Checks

**Rule:** Provenance must match actual data source

**Implementation:**
- Validation checks on data ingest
- Consistency checks on API responses
- Automated tests for provenance correctness
